# ДЗ 9. Сервис аутентификации

Взял CRUD из ДЗ 7 и добавил маршрутизатор `/auth` с регистрацией, входом и выходом. Эндпоинты `/students` теперь работают только с токеном, без него ответ 401

Из вариантов авторизации сделал вход по токену (user_token) и права только на чтение для части пользователей

## Как запустить

```bash
pip install -r requirements.txt
python main.py
```

Как и в ДЗ 7, при первом запуске создается `students.db` и в нее грузится `students.csv`. Пользователи и токены лежат в той же базе в таблицах `users` и `tokens`. Чтобы начать с чистых данных, можно удалить `students.db`

Документация: http://127.0.0.1:8000/docs. Там есть кнопка Authorize, в нее вставляется токен из `/auth/login`, и дальше запросы из документации идут уже с ним

Тесты - `pytest`, они работают со своей базой во временной папке

## Эндпоинты

| Метод | Путь | Что делает | Кому можно |
|---|---|---|---|
| POST | `/auth/register` | регистрация, ответ 201 | всем |
| POST | `/auth/login` | вход, в ответе токен | всем |
| POST | `/auth/logout` | выход, токен перестает работать, ответ 204 | с токеном |
| GET | `/students/`, `/students/{id}` | список и одна запись | с токеном |
| POST, PUT, PATCH, DELETE | `/students/...` | создание, изменение, удаление | с токеном и без read_only |

Токен передается в заголовке `Authorization: Bearer <токен>`

Коды ошибок:
- 401 - нет токена, токен неверный или после выхода, неверный логин или пароль
- 403 - пользователь с read_only пытается что-то поменять
- 409 - при регистрации имя уже занято
- 404 и 422 - как в ДЗ 7

## Как я понял неоднозначные места

- "Незарегистрированные не имеют доступа" понял так: доступ только у того, кто зарегистрировался и вошел, то есть прислал действующий токен
- Токен - случайная строка из `secrets`, хранится в базе. Выход удаляет его из базы, поэтому старый токен сразу перестает работать. Если войти несколько раз, будет несколько токенов, выход завершает только текущую сессию
- Пароль в базе не храню, только соль и хеш через `pbkdf2_hmac` из стандартной библиотеки, поэтому новых зависимостей нет
- Права только на чтение задаются при регистрации флагом `read_only`. В настоящем сервисе такое выдавал бы админ, но для учебного задания так проще проверить. Понятно, что так ограничение легко обойти, просто зарегистрировавшись еще раз без флага
- Логин от 3 до 50 символов, пробелы по краям у него обрезаются. Пароль от 6 до 100 символов, берется как есть
- Срок жизни токена и refresh не делал, это следующий уровень сложности

## Пример

```bash
curl -X POST http://127.0.0.1:8000/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"username": "artemiy", "password": "qwerty123"}'
```

Ответ: `{"id": 1, "username": "artemiy", "read_only": false}`

```bash
curl -X POST http://127.0.0.1:8000/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username": "artemiy", "password": "qwerty123"}'
```

Ответ: `{"access_token": "...", "token_type": "bearer"}`

```bash
curl http://127.0.0.1:8000/students/1 -H 'Authorization: Bearer <токен>'

curl -X POST http://127.0.0.1:8000/auth/logout \
  -H 'Authorization: Bearer <токен>'
```

Без токена: `{"detail": "Нужно войти: /auth/login"}` и код 401. Пользователь с `read_only` на DELETE получает 403 `{"detail": "У пользователя права только на чтение"}`
